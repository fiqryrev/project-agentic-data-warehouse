## da-0001

**Customer city casing in the shop source**

Tags: shop, customers, city, casing, defect, data-quality. Source: `.agents/knowledge/entries/da/da-0001-customer-city-casing.md`.

## Meaning

`data_lake_layer.shop__customers.city` is a city name. 10% of the customer rows written each day (new
customers and the versions of customers who moved) carry the city all upper case or all lower
case (`JAKARTA`, `bandung`). It is the same city as its title-case spelling; nothing else
differs. `generator/DEFECTS.md` says "new customers"; the generator samples over every row it
writes that day.

### Counts

On the 3-day CI dataset (`make dbt-ci`, 2026-01-01 to 01-03): 208 of 2,088 customer rows.

```sql
select count(*) filter (where city = upper(city) or city = lower(city)) as miscased,
       count(*) as customer_rows
from data_lake_layer.shop__customers;
```

### Terms

"Casing", "upper-case city", "messy city names". Downstream, `staging__shop__customers` and
every warehouse table carry the title-case city as `city_name`.

### Data quality

Fixed in staging with the `title_case` macro, so filter `city_name` in `data_staging_layer` and `data_warehouse_layer`
on the title-case value; filter the lake only with `lower(city)`. DuckDB has no `initcap`, though
`generator/DEFECTS.md` names it as the way to spot the defect; use the query above.

## da-0002

**Exact duplicate order rows in the shop source**

Tags: shop, orders, duplicates, defect, data-quality. Source: `.agents/knowledge/entries/da/da-0002-duplicate-order-rows.md`.

## Meaning

0.5% of a day's `data_lake_layer.shop__orders` rows appear twice, identical in every column including
`_dt`. They are one order state written twice, not two events.

### Counts

On the 3-day CI dataset (`make dbt-ci`): 12 duplicated rows.

```sql
select count(*) as duplicated_rows
from (select order_id, updated_at, order_status, _dt
      from data_lake_layer.shop__orders group by all having count(*) > 1);
```

### Terms

"Duplicate orders", "double rows". Not the same as late rows (da-0003), where the copy
arrives in a later partition.

### Data quality

Every staging model selects distinct rows, so the exact copies are gone from staging. That does
not make `count(*)` an order count there: `staging__shop__orders` keeps one row per order
*state*, so an order that was placed, paid and shipped has three rows. `count(*)` counts orders
only on the current-state fact, `fact__sales__orders` (one row per order); on the lake or in
staging use `count(distinct order_id)`.

## da-0003

**Late order rows land in a later partition**

Tags: shop, orders, late-rows, partition, defect, data-quality. Source: `.agents/knowledge/entries/da/da-0003-late-order-rows.md`.

## Meaning

2% of a day's order rows are held back 1 to 3 days and land in a later partition, sometimes
after a newer row of the same order. Such a row has `updated_at::date < _dt`. Its status is
older than the order's current one.

### Counts

On the 3-day CI dataset (`make dbt-ci`): 10 late rows out of 2,532 order rows (the first day
cannot receive late rows, so the share is below 2%).

```sql
select count(*) filter (where updated_at::date < _dt) as late_rows,
       count(*) as order_rows
from data_lake_layer.shop__orders;
```

### Terms

"Late rows", "late-arriving data", "out-of-order updates".

### Data quality

Never take "the row from the latest partition" as current. `fact__sales__orders` picks the
latest `updated_at` (then `_dt`), so a late row never wins. At the edge of the loaded dates a
held-back row may not have arrived yet, so payments can point at an order missing from
`fact__sales__orders`; those relationship tests warn.

## da-0004

**Orphan product keys on order lines**

Tags: shop, ledger, order_items, products, orphan-keys, defect, data-quality. Source: `.agents/knowledge/entries/da/da-0004-orphan-product-keys.md`.

## Meaning

About 0.2% of order lines (`shop.order_items.product_id`, and the ledger's
`invoice_lines.product_ref`) point at a product that never existed. Orphan ids start at
9,000,000. These lines are left out of seller settlements: there is no seller to pay.

### Counts

On the 3-day CI dataset (`make dbt-ci`): 3 orphan lines out of 2,971.

```sql
select count(*) filter (where product_id >= 9000000) as orphan_lines,
       count(*) as lines
from data_lake_layer.shop__order_items;
```

### Terms

"Orphan keys", "unknown product", "missing product".

### Data quality

Kept in staging and warehouse; their `relationships` and `not_null` tests warn instead of
failing. An inner join to `dim__sales__products` drops these lines, so revenue by category is
slightly below total revenue. `product_version_key` is null for them.

## da-0005

**Status shipped renamed in_transit from 2026-06-01**

Tags: shop, orders, shipments, status, rename, defect, data-quality. Source: `.agents/knowledge/entries/da/da-0005-shipped-renamed-in-transit.md`.

## Meaning

`order_status` and `shipment_status` say `shipped` in partitions before 2026-06-01 and
`in_transit` from 2026-06-01, late rows included. Same state, new name. Both values exist across
history, never in one partition.

### Counts

Generated and loaded 2026-05-31 and 06-01 into a scratch file (`uv run python -m generator
--start 2026-05-31 --end 2026-06-01`, then the loader): 666 `shipped` order rows on 05-31,
619 `in_transit` on 06-01, none of the other value on either day.

```sql
select _dt, order_status, count(*)
from data_lake_layer.shop__orders
where order_status in ('shipped', 'in_transit')
group by all order by all;
```

### Terms

"Shipped", "in transit", "on the way". Use `in_transit` downstream.

### Data quality

Staging maps `shipped` to `in_transit` across history, so filter staging and warehouse on
`in_transit` only. A lake filter on one value misses half the history (rule: verify a literal
before filtering on it).
