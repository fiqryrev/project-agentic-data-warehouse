## de-0001

**Build dimension history from the lake, not from dbt snapshots**

Tags: dbt, scd2, history, dimensions, backfill, snapshots. Source: `.agents/knowledge/entries/de/de-0001-history-from-the-lake.md`.

## Rule

Slowly changing dimensions (`valid_from_at`, `valid_to_at`, `is_current`) are computed with window
functions over every version the lake holds, not with dbt snapshots.

### Why

A snapshot records build time, so rebuilding after a backfill gives a different history than
the first run. The lake is append-only by `_dt` and keeps every version the source wrote, so a
full rebuild reproduces the same history every time.

### How to apply

Make the source write a new row on each change (with `updated_at`), keep all of them in staging,
and derive `valid_from_at = updated_at`, `valid_to_at = lead(updated_at)`,
`is_current = valid_to_at is null`. Test with `scd2_valid` (no overlap, one current row per key).

### Example

`dim__sales__customers`: one row per customer version; `fact__sales__order_items` joins the
version valid at the order's timestamp.

## de-0002

**Name the DuckDB file dwh.duckdb, never after a schema**

Tags: duckdb, catalog, schema, build-file, naming. Source: `.agents/knowledge/entries/de/de-0002-build-file-name.md`.

## Rule

Every build file is `data/<target>/dwh.duckdb` (catalog `dwh`); no DuckDB file is named after
one of its schemas.

### Why

DuckDB names the catalog after the file. A file called `warehouse.duckdb` made
`warehouse.<table>` ambiguous between the catalog and the `warehouse` schema.

### How to apply

Keep the file name `dwh.duckdb` in the loader, the Makefile, `dbt/profiles.yml` and later
Airflow. Qualify tables as `<schema>.<table>`, or `dwh.<schema>.<table>` across attached files.

### Example

`make load` writes `data/dev/dwh.duckdb`; `make dbt-ci` builds `data/ci/dwh.duckdb`.

## de-0003

**Load a lake day in one transaction with a deterministic batch id**

Tags: loader, lake, transaction, idempotent, batch, audit-columns. Source: `.agents/knowledge/entries/de/de-0003-one-transaction-per-day.md`.

## Rule

A partition date loads in one transaction: for each table, delete that `_dt`, insert the new
rows. `_batch_id` is `<date>-<first 12 hex of the manifest SHA-256>`.

### Why

If any table fails (checksum, schema drift), no table of that day changes, so the lake is never
half-loaded. Same input gives the same batch id, so loading a day twice leaves counts unchanged
and a reload is visible only in `_loaded_at`.

### How to apply

Reload a day by rerunning the loader for that date; never patch lake rows by hand. Compare
`_batch_id` to tell whether two loads read the same files.

### Example

`uv run python -m loader --date 2026-01-02` twice: the same row counts and `_batch_id`, a
newer `_loaded_at`.

## de-0004

**Governance checkers read dbt models statically with DuckDB's parser**

Tags: governance, checkers, dbt, parser, ci, select-star. Source: `.agents/knowledge/entries/de/de-0004-read-dbt-statically.md`.

## Rule

The model checkers (`check_naming`, `check_bundle`, `check_layers`, `check_audit_columns`) read
SQL and YAML files without running dbt or opening a database. Output columns come from
DuckDB's `json_serialize_sql` parse tree of the Jinja-reduced SQL.

### Why

They run in seconds in the governance job and need no build. DuckDB's own parser handles its
syntax (`qualify`, lambdas, `filter`) with no new dependency.

### How to apply

End every model with an explicit select list and alias every expression; a final `select *`
fails `check_bundle`, since its columns cannot be known statically. A new macro used in a
select list must be aliased (`{{ my_macro(x) }} as y`).

### Example

`uv run python -c "from helpers.dbtlib import load_models; print(load_models()[0].columns)"`
lists a model's output columns.

## de-0005

**The warehouse assumes the lake was loaded from the epoch**

Tags: dbt, lake, backfill, epoch, airflow, catchup. Source: `.agents/knowledge/entries/de/de-0005-load-from-the-epoch.md`.

## Rule

Build the warehouse only on a lake loaded from 2026-01-01, the generator's epoch.

### Why

Sellers and campaigns are written once, on their creation day. A window that starts later has
order lines pointing at sellers it never loaded; a try from 2026-05-15 to 06-28 failed four
relationship tests.

### How to apply

Backfills start at 2026-01-01 (`make generate` and `make load` defaults, `make dbt-ci`).
Airflow's `warehouse_daily` uses `catchup=True` from the epoch (M7).

### Example

`make dbt-ci` loads 2026-01-01 to 01-03 before `dbt build --target ci`.
